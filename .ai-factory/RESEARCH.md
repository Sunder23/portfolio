Topic: Реорганизация структуры src/ без перехода на FSD ("Вариант B" — точечные фиксы поверх существующего Modular Monolith)
Goal: Устранить конкретные раздражители в текущей структуре (простыня Home/index.tsx, раздутые components/ и admin/components/, контексты вперемешку с обычными компонентами) без миграции на Feature-Sliced Design — сохранить решение из ARCHITECTURE.md (Modular Monolith), т.к. проект соло, без бэкенда, близок к завершению по ROADMAP (осталось только Этап 4 — лиды).
Constraints: Не ломать конвенцию "компонент = папка" и алиас `@/*`. Не трогать `components/ui/*` (shadcn CLI ожидает плоскую структуру). Не переименовывать `app/data/` в `store` (это файловая БД, не клиентский стейт — терминологически другое). `App.tsx` остаётся плоским (уже задокументированное исключение).
Decisions:
- FSD целиком отклонён как избыточный для масштаба проекта (соло-разработчик, 6 страниц + admin, без бэкенда, проект в стадии завершения по ROADMAP) — полная миграция на app/pages/widgets/features/entities/shared дала бы отрицательный ROI и конфликтовала бы с исключением для components/ui/*.
- `lib/data.ts` (чтение) и `admin/lib/github.ts` (запись) уже являются единственными точками доступа к данным — жалоба "API-слой перемешался" не подтвердилась фактическим состоянием кода, менять не нужно.
- `types.ts` уже централизован (89 строк) — резать по доменам рано, делать только когда файл реально станет большим.
- **Home/index.tsx (313 строк, 1 функция, 12 секций рендера)** → разбить на секции-компоненты внутри `pages/Home/` (HeroSection, StatsSection, ServicesSection, ProcessSection, StackSection, TechHighlightsSection, FeaturedProjectsSection, CommitsSection, ExperienceSection, TestimonialsSection, FaqSection, CtaSection — имена ориентировочные, по существующим блокам разметки). `TerminalCursor` и `CommitActivityGrid` (сейчас в `components/`, единственный потребитель — Home) переезжают внутрь своих секций при декомпозиции.
- Page-local константы (`slice(0, 2)`, `padStart(2, '0')` и т.п. из Home) → `pages/Home/constants.ts`, не глобальное constants-пространство.
- **Правило для components/ и admin/components/: "1 потребитель → компонент колокейтится с этим потребителем; 2+ потребителя (реально shared) → остаётся в components/".** Применяется строго, кроме двух явных исключений (см. ниже).
- Публичная часть, `components/` (было 13 папок + ui/) → остаётся реально shared: `CommandLabel` (5 стр.), `MarkdownContent` (2 стр.), `ProjectCard` (3 стр.), `LocaleSwitcher` (2 потр.). Переезжают: `ProjectFilters` → `pages/Projects/ProjectFilters/` (единств. потребитель), `ThemeToggle` → `components/Nav/ThemeToggle/` (единств. потребитель — Nav).
- **Исключение №1 (явное, осознанное):** `Nav/`, `Footer/`, `Scanline/` остаются плоско в `components/`, не вкладываются под `PublicLayout/`, хотя формально у каждого один потребитель (сам `PublicLayout`) — это части одного layout-root, а не самостоятельные единицы.
- **Контексты — новое правило:** любой файл с `createContext` живёт в своей папке `context/` (не в `components/`), независимо от количества потребителей (у контекстов по природе много потребителей через `useContext`, правило "1 потребитель" сюда неприменимо). `admin/components/AdminAuthContext/`, `AdminLocaleContext/`, `AdminDraftContext/` → `admin/context/AdminAuthContext/`, `AdminLocaleContext/`, `AdminDraftContext/` (имя `AdminDraftContext` НЕ меняется на `AdminDraftStore`, хотя по факту это полноценный стор на 214 строк с бизнес-логикой — осознанно оставлено ради консистentности с Context API-механизмом).
- **Исключение №2 (явное, осознанное):** `hooks/useLocale.ts` (10 строк, `createContext` без единой строки JSX) остаётся как есть, не выносится в `context/` — слишком тривиален, чтобы ради него создавать новую папку.
- `admin/components/` (было 12 папок, 3 из них контексты — см. выше) → после переноса контекстов остаётся 9. Реально shared: `LocalizedField` (5 редакторов), `ImageUploadField` (2 редактора + композиция внутри GalleryUploadField). Колокейт: `RichTextEditor` → `admin/components/LocalizedField/RichTextEditor/` (единств. потребитель); `TaxonomyCheckboxes` → `admin/editors/ProjectForm/TaxonomyCheckboxes/`; `GalleryUploadField` → `admin/editors/ProjectForm/GalleryUploadField/` (оба — единственный потребитель ProjectForm; GalleryUploadField продолжает импортировать shared ImageUploadField извне).
- `AdminLayout` — layout-root (аналог `PublicLayout`), единственный потребитель `pages/Admin/index.tsx` по определению одного роута — это норма, НЕ колокейтится внутрь pages/Admin/.
- В отличие от исключения №1, для детей AdminLayout (`AdminSidebar`, `TokenGate`, `SaveAllButton` — каждый с единственным потребителем AdminLayout) решено НЕ делать симметричное исключение: они строго вкладываются → `admin/components/AdminLayout/AdminSidebar/`, `AdminLayout/TokenGate/`, `AdminLayout/SaveAllButton/`.
Open questions: Не прогнана та же линза колокейта по `admin/editors/` и `admin/lib/` — пользователь спрашивал, есть ли смысл, но не решил, продолжать копать или переходить к плану.
Success signals: Home/index.tsx разбит на секции без потери поведения; components/ и admin/components/ содержат только реально переиспользуемые компоненты + два задокументированных исключения (Nav/Footer/Scanline, useLocale.ts); все createContext-файлы (кроме useLocale.ts) лежат в context/ / admin/context/; все существующие тесты (colocated *.test.tsx) продолжают проходить после переездов файлов (только импорты/пути, без изменения логики).
Next step: /aif-plan на реализацию (можно продолжить исследование admin/editors/ и admin/lib/ той же линзой перед планированием, если пользователь захочет).

### 2026-07-18 12:00 — Батчинг сохранений в админке: staging-стор + отложенная загрузка картинок
What changed: Разобрали, что текущая архитектура (Contents API + `cancel-in-progress` в deploy.yml) уже безопасна для нескольких независимых правок за сессию (разные файлы = нет sha-конфликтов, финальный CI run деплоит актуальный HEAD). Спроектирована плавающая кнопка "Сохранить всё" поверх in-memory staging (без localStorage — приемлемо для одного юзера) и отложенная загрузка картинок (вариант B) для одиночного поля и галереи.
Key notes: Существующее разделение `compressImage()`/`uploadImageToGithub()` в коде уже готово к переносу сетевой загрузки в момент финального Save — рефакторинг дешевле, чем казалось на старте. `GalleryUploadField` переиспользует `ImageUploadField` на каждый элемент массива, отдельной логики для галереи не нужно. Вариант B заодно чинит существующий orphan-баг с картинками (сегодня фото коммитится в GitHub сразу при выборе файла, до Save поста).
