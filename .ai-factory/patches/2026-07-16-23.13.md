# Admin session forced back to TokenGate on transient network errors

**Date:** 2026-07-16 23:13
**Files:** app/src/admin/AdminLayout.tsx, app/src/admin/TokenGate.tsx
**Severity:** medium

## Problem

Admin users were bounced back to the TokenGate login screen with a "network
error" message, sometimes on every page load, even though their stored PAT
was still valid. Console showed repeated
`[admin/TokenGate] validation failed (network error)` /
`[admin/github] validating token for Sunder23/portfolio` cycles.

## Root Cause

`AdminLayout.tsx` runs `validateToken(token)` on mount to check the stored
session. `validateToken()` (in `github.ts`) either resolves `false` for a
genuine non-2xx response (e.g. 401 — real invalid token) or **throws** when
`fetch()` itself fails (offline, blocked request, CORS preflight failure,
DNS issue) — a purely network-level failure that says nothing about whether
the token is actually valid.

`AdminLayout`'s `.catch()` handler treated both cases identically: it set
`valid = false`, which hides the whole app behind `TokenGate` — functionally
equivalent to a forced logout — for a transient connectivity blip that has
nothing to do with the token's validity. This was inconsistent with
`useAdminSave.ts`, which already correctly distinguishes a genuine
`GithubAuthError` (401 → `logout()`) from any other error (toast, session
kept).

Separately, `TokenGate.tsx` never trimmed the pasted PAT before using it.
A trailing newline/space from a copy-paste (common from password managers
or terminals) makes `fetch()` throw while constructing the `Authorization`
header — which also surfaced as the same generic "network error" message.
Its `catch { ... }` block discarded the actual caught error entirely, so
this whole failure class was undiagnosable from the console.

## Solution

- `AdminLayout.tsx`: in the mount-time `validateToken` `.catch()`, no longer
  treat a thrown (network-level) error the same as a definitive invalid
  token. Log it and set `valid = true` (trust the locally stored token)
  instead of forcing `TokenGate`. Only a resolved `false` (real 401/non-ok
  response, handled in `.then`) triggers `logout()`.
- `TokenGate.tsx`: `.trim()` the input value before calling `validateToken`
  and before `setToken`, and log the actual caught error (`err`) instead of
  swallowing it.

## Prevention

- When a validation/auth check can fail for two structurally different
  reasons (definitively invalid vs. couldn't verify due to network), keep
  those as distinct code paths — don't let a generic `catch` collapse them
  into the same user-facing outcome.
- Always trim free-text credential/token inputs before using them in HTTP
  headers; a stray newline or space turns into a confusing low-level fetch
  error instead of a clear validation message.
- Never write a bare `catch { ... }` that discards the error object —
  always capture and log it, even if the user-facing message stays generic.
