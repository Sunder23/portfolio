# Project delete pushed immediately and Save-All counter desynced; drafts didn't survive navigation

**Date:** 2026-07-18 23:38
**Files:** app/src/admin/components/AdminDraftContext/index.tsx, app/src/admin/components/AdminDraftContext/AdminDraftContext.test.tsx, app/src/admin/components/SaveAllButton/index.tsx, app/src/admin/editors/ProjectsList/index.tsx, app/src/admin/editors/ProjectsList/ProjectsList.test.tsx, app/src/admin/editors/TaxonomyEditor/TaxonomyEditor.test.tsx, docs/admin-workflow.md
**Severity:** medium

## Problem

Reported: "global save doesn't work properly — deleting a project pushes a commit immediately, and the counter on the 'Save all' button doesn't update." Follow-up from the user during investigation revealed a second, more fundamental symptom: an unsaved edit (e.g. adding a Taxonomy term) disappeared after navigating to another admin section (e.g. "Add project") and back.

## Root Cause

Three related issues in the batch-save draft store (`AdminDraftContext`):

1. `ProjectsList`'s delete handler never talked to `AdminDraftContext` at all — it called `deleteFile()` directly via `useAdminOperation`, exactly the same anti-pattern already fixed for `TaxonomyEditor` in commit `ee2a047`, just not carried over to Projects.
2. `captureBaseline(path, data)` unconditionally overwrote both `data` and `baseline` on every call, instead of only on a path's first load in the session. Any component that mounts and calls `useEditorData(path)` — including a purely read-only consumer, like `ProjectForm` loading `taxonomies.json` just to populate its dropdowns — re-fetched from GitHub and reset the entry, silently discarding whatever was staged there. This is why editing Taxonomies then navigating to "Add project" (which itself reads `taxonomies.json`) wiped the taxonomy edit.
3. The draft store was in-memory only (`useState({})`), so even without bug #2 it would not survive a reload — the user explicitly asked for this to be backed by `localStorage` instead.

## Solution

- `captureBaseline` now skips writing if an entry already exists for that path — a baseline is captured once per session per path; existing (dirty or not) state is left alone until `clearEntry` runs (on successful save).
- `AdminDraftContext`'s `entries` are now mirrored to `localStorage` (key `admin-draft-v1`) on every change, and hydrated from it on mount. `PendingImage` blobs (staged-but-unuploaded images) aren't JSON-serializable, so they're base64-encoded on write and rebuilt into a fresh `Blob` + fresh `URL.createObjectURL` preview on read. `localStorage.setItem` quota errors are caught and surfaced via a toast rather than silently losing the whole draft.
- `ProjectsList`'s delete now stages through the same draft store (`captureBaseline` + `setEntry` + `registerFlush`) instead of calling `deleteFile()` directly — it participates in the "Save all" counter and only actually deletes when its registered flush runs.
- `SaveAllButton` now toasts an explicit message when a dirty path has no registered flush (can happen right after a reload restores a draft before its owning editor has mounted), instead of silently skipping it.

## Prevention

- When a "point operation" (create/delete/rename outside a form) is added for any entity, check whether it should route through `AdminDraftContext` like every other edit — bypassing it reintroduces exactly this class of bug (already happened twice: Taxonomies, then Projects).
- Any store method named `captureBaseline`/`initialize`/`load*` that's called from a `useEffect` on every mount should be audited for whether repeated calls are idempotent — "runs once conceptually" and "runs once mechanically" are not the same thing when the owning component can remount.
- When adding persistence to a React Context backed by `useState`, check test files that mount fresh provider instances per test (`render(<Provider>...)` per `it`) — shared browser storage (`localStorage`) can leak state across tests unless explicitly cleared in `afterEach`.
