# Each staged image (and a project rename) produced its own commit/deploy; admin didn't refresh after saving

**Date:** 2026-07-19 00:13
**Files:** app/src/admin/lib/github.ts, app/src/admin/lib/github.test.ts, app/src/admin/lib/resolvePendingImages.ts, app/src/admin/lib/resolvePendingImages.test.ts, app/src/admin/hooks/useEditorData.ts, app/src/admin/editors/ProjectForm/index.tsx, app/src/admin/editors/projectsData.ts, app/src/admin/editors/projectsData.test.ts, app/src/admin/components/SaveAllButton/index.tsx, docs/admin-workflow.md
**Severity:** low

## Problem

Reported via a screenshot of the GitHub Actions run list: saving a project with 2 new gallery images produced 4 separate workflow runs from one "Save all" click — `chore(uploads): add <uuid>.webp` x2, `admin: update taxonomies.json`, `admin: update projects.json`. Each staged image was its own commit (and its own GitHub Pages deploy), on top of the entity's own commit. Separately: the admin page's local state (project lists, form fields) stayed stale after a successful save — nothing ever reloaded it, and the user assumed (incorrectly) that this was tied to waiting for the GitHub Pages deploy to finish.

## Root Cause

`admin/lib/github.ts`'s `uploadPendingImage()` used the Contents API's single-file PUT to upload a staged image — that's inherently one commit per file, called once per PendingImage inside `resolvePendingImages()`, before the entity's own `saveFile`/`createFile` PUT. There was no mechanism to combine an entity's JSON with its own staged images into a single commit, because the Contents API has no multi-file write. Project rename had the same shape for a different reason: it was implemented as `createFile(newPath)` + `deleteFile(oldPath)`, two independent commits.

Separately, the admin never reloaded or re-fetched after `SaveAllButton` finished — each editor kept whatever was in `AdminDraftContext`/component state from before the save, so the UI didn't reflect the just-saved GitHub state until a manual refresh.

## Solution

- Added a Git Data API path to `github.ts`: `createImageBlob()` creates a blob without committing; `commitFiles()` bundles any number of `{path, content}` / `{path, blobSha}` / `{path, delete: true}` entries into one commit (blob → tree → commit → ref update), with the same one-retry-on-conflict pattern as the Contents API (422 non-fast-forward ≈ 409 sha mismatch).
- `resolvePendingImages()` now creates blobs (via the injected `upload` callback) instead of uploading+committing immediately, and returns both the resolved value *and* the list of image blob entries to commit alongside it. Its `ResolvedImageEntry` carries both the repo path (commit tree entry) and the public runtime URL (substituted into the JSON) — conflating these two was an early version of this fix and would have silently broken every future `<img src>` by storing the repo path instead of the public URL; caught via `tsc` type errors, not a review, so treat this as a live edge worth double-checking if the pattern is copied elsewhere.
- `useEditorData`'s generic flush (Profile/Skills/Taxonomies) and `ProjectForm`'s flush use `commitFiles` when there's at least one staged image, falling back to the cheaper plain `saveFile`/`createFile` when there are none — most saves stay on the simpler, more battle-tested 2-call path.
- Extracted the "which GitHub call(s) to make" decision out of `ProjectForm` into a pure `buildProjectCommitPlan()` in `projectsData.ts`, specifically so it's unit-testable without rendering the (TipTap-heavy) form component.
- Project rename now always goes through `commitFiles` (create-new + delete-old + any images, one commit) instead of two sequential commits — this also closes a partial-failure window that existed before (a crash between the create and the delete could leave both files present).
- `SaveAllButton` reloads the page ~1.2s after a successful save (not waiting for the untracked GitHub Pages deploy) so every open editor re-fetches fresh data instead of showing stale local state.

## Prevention

- When a generic resolver function returns "a path" for something that has both a storage location and a different public-facing representation (repo path vs. public URL, internal ID vs. slug, etc.), name the two fields explicitly in the return type rather than a single ambiguous `path` — the compiler catches a shape mismatch but not a silent double-purposing of one field.
- When extracting business logic out of a component specifically to make it testable, prefer a pure function over trying to render the component in tests — cheaper to write and run, and doesn't depend on unrelated libraries (TipTap here) working under jsdom.
- Multi-file atomic writes to GitHub require the Git Data API, not the Contents API — worth remembering as the default reference point next time "combine N commits into one" comes up against `github.ts`.
