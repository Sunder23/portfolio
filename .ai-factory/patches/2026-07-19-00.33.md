# description field ignored locale switch; new project page was dirty on open; localStorage persist race

**Date:** 2026-07-19 00:33
**Files:** app/src/admin/components/RichTextEditor/index.tsx, app/src/admin/editors/ProjectForm/index.tsx, app/src/admin/editors/ProjectForm/ProjectForm.test.tsx, app/src/admin/components/AdminDraftContext/index.tsx, app/src/admin/components/AdminDraftContext/AdminDraftContext.test.tsx
**Severity:** medium

## Problem

Reported: (1) on `/admin/projects/new`, switching the uk/ru/en locale tab didn't change what the `description` rich-text field showed. (2) After saving, the floating "Save all" button stayed visible showing `(1)` instead of disappearing — the user correctly suspected this was tied to simply opening the "Add project" page, not to an actual unsaved edit.

## Root Cause

1. `RichTextEditor` passes `value` to TipTap's `useEditor({ content: value })`. TipTap only consumes `content` once, at editor creation — it does not react to the prop changing afterwards. `LocalizedField` swaps `value` when the locale tab changes, but the mounted editor instance kept showing whatever it was initialized with.

2. `ProjectForm` has an effect that auto-fills the slug field from the title: `setSlug(slugify(autoSlugSource))`, gated on `!slugLocked`. `slugify('')` deliberately falls back to `'untitled'` (so a save with no title still gets a usable slug — see `lib/slug.ts`). That effect ran unconditionally on mount, before any title was typed, writing `'untitled'` into the draft's `slug` field immediately — while the captured baseline had `slug: ''`. The mismatch made `isDirty` true from the moment the page opened, with zero user input. The slug *display* already independently falls back to `{slug || 'untitled'}`, so this write was redundant on top of being the bug.

3. Separately (found while investigating #2): `AdminDraftContext`'s `useEffect(() => { void persistEntries(entries) }, [entries])` had no protection against out-of-order async completion. Serializing entries to localStorage is async (staged images go through `FileReader`), so two entries changes close together — e.g. every keystroke while typing a title — each fire off their own persist call, and a slower earlier one can finish writing *after* a faster later one, clobbering localStorage with already-superseded data. Confirmed this fires constantly during normal typing (visible in the new `ProjectForm.test.tsx` test's logs: `discarding stale localStorage write` on nearly every keystroke), not just as a rare edge case.

## Solution

- `RichTextEditor`: added a `useEffect` that calls `editor.commands.setContent(value)` when `value` diverges from `editor.storage.markdown.getMarkdown()`. Comparing against the editor's own current content (not the previous prop) is what avoids fighting the user's typing — `onUpdate` → `onChange` → this effect re-running with a `value` that already matches skips `setContent`, so the cursor isn't reset on every keystroke.
- `ProjectForm`: gated the auto-slug effect on `autoSlugSource.trim()` being non-empty, so nothing is written to the draft until there's a real title.
- `AdminDraftContext`: added a monotonic sequence-number ref (`persistSeqRef`); each effect run captures its own sequence number and only commits its `localStorage.setItem`/`removeItem` if no newer entries change has started since — a superseded write is silently discarded instead of applied.

## Prevention

- Any third-party editor library wrapped in a "controlled component" shape (`value`/`onChange`) needs to be checked for whether its "initial value" prop is actually reactive — many (TipTap included) only consume it once. Grep for `useEditor(` in this codebase before assuming a `value` prop change is enough.
- A `slugify`/`normalize`-style fallback default meant for "value at save time" should not be round-tripped through a live auto-preview effect that writes back into the source of truth — display-only fallbacks (`value || 'default'` in JSX) don't have this problem; effects that call a setter do.
- Any effect that persists to an external store asynchronously on every state change needs an explicit staleness guard once more than one such effect can be in flight at once — "it usually finishes in order" is not a correctness argument.
