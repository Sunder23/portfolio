# Home page silently loses commits list and activity heatmap under GitHub API rate limiting

**Date:** 2026-07-20 17:10
**Files:** app/src/lib/commits.ts, app/src/lib/commits.test.ts
**Severity:** medium

## Problem

On the Home page, the recent-commits list and the commit-activity heatmap
sometimes render nothing, with no visible error to the user. Confirmed live:
`curl` against `https://api.github.com/repos/Sunder23/portfolio/commits` from
the dev environment IP returned `403` with `X-RateLimit-Remaining: 0`.

## Root Cause

`getRecentCommits` and `getCommitActivity` in `app/src/lib/commits.ts` call
the unauthenticated GitHub REST API directly from the browser on every page
mount, with no client-side caching. Unauthenticated requests are capped at
60/hour **per IP**. A single Home page load fires 2+ requests (1 for recent
commits, 1–5 paginated for the activity grid), so the budget is exhausted
quickly — in dev via React StrictMode's double-effect invocation and hot
reload, and in production whenever multiple visitors share an IP (corporate
NAT, etc.). Both fetchers already caught errors, but only logged them and
returned `[]`, which `Home/index.tsx` treats as "nothing to show" — the
`{commits && commits.length > 0 && ...}` guard hides the whole section
silently instead of surfacing any error state.

## Solution

Added a small localStorage-backed cache (`readCache`/`writeCache`,
`CACHE_FRESH_MS = 15min`) shared by both fetchers:

- On call, if a cached value is younger than the freshness window, return it
  without hitting the network — cuts the request count per browsing session
  drastically.
- On a failed fetch (non-OK response or thrown error, including a 403 rate
  limit), fall back to the last cached value even if stale, instead of `[]`.
  Only returns `[]` when there is no cache at all (first-ever load during a
  rate limit window).

This doesn't fix GitHub's rate limit itself, but turns "rate limited →
section disappears" into "rate limited → last known data keeps showing."

## Prevention

- Any client-side fetch to a rate-limited third-party API should cache
  successful responses and prefer stale-cache-over-nothing on failure, not
  just log-and-return-empty.
- When a UI section is conditionally hidden based on fetched data being
  empty, consider whether "empty because there's genuinely nothing" and
  "empty because the fetch failed" need to be distinguishable to the user.
