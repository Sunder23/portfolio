# Admin Save Workflow — GitHub Contents API

Админка этого сайта не имеет бэкенда: любое сохранение — это коммит в
репозиторий через GitHub Contents REST API из браузера, аутентифицированный
fine-grained PAT пользователя. Источник требований — `.ai-factory/DESCRIPTION.md`
и `PLAN.md` (разделы «Админка», «Подводные камни»).

## Авторизация (TokenGate)

- `src/admin/TokenGate.tsx` — единственная точка входа в `/#/admin`.
- PAT вводится пользователем и **проверяется** запросом
  `GET https://api.github.com/repos/{owner}/{repo}` (не просто сохраняется
  без проверки).
- Токен хранится только в `localStorage`, никогда не попадает в код,
  переменные окружения бандла или коммиты.
- Кнопка «выйти» очищает `localStorage` и возвращает на `TokenGate`.
- При любом `401` от Contents API — сброс на `TokenGate`, а не необработанное
  исключение и не бесконечный ретрай.

## Клиент записи (`src/admin/github.ts`)

Генерик-функция, работающая с любым файлом по пути (не завязана на
конкретную сущность — так масштабируется на новые типы контента):

```ts
async function saveFile(path: string, content: object | string, message: string) {
  const { sha } = await getFileSha(path);           // 1. GET текущий sha
  return putFile(path, content, message, sha);       // 2. PUT с этим sha
}
```

### Алгоритм (обязательный порядок)

1. `GET /repos/{owner}/{repo}/contents/{path}` → взять текущий `sha`.
2. `PUT /repos/{owner}/{repo}/contents/{path}` с телом
   `{ message, content: base64(json), sha }`.
3. При ответе `409` (sha устарел): повторить шаги 1–2 **один раз**. Если
   повторная попытка тоже даёт `409` — показать пользователю явную ошибку
   («файл изменён параллельно, обновите страницу»), не откатывать молча и не
   зацикливаться на ретраях.
4. Осмысленный commit message для каждой сущности, например:
   `admin: update projects.json (edit "viva-realtyexpert")`.

### Что НЕ делать

- Не кэшировать `sha` между операциями сохранения дольше, чем на время одного
  сохранения — он должен читаться заново перед каждым PUT.
- Не делать PUT без предварительного GET (иначе первый же 409 неизбежен при
  параллельной правке).
- Не глотать ошибки API молча — админка должна показывать понятный тост об
  успехе/неудаче.

## Изображения

- Загрузка файла → сжатие в браузере через `<canvas>` в **webp**
  (max-width 1600px, quality ≈0.8) → base64 → тот же алгоритм PUT
  (GET sha → PUT), путь `public/uploads/{slug}-{n}.webp`.
- GitHub Contents API ограничен ~1 МБ на файл через JSON PUT — сжатие
  обязательно перед отправкой, а не опционально.
- Поля `cover`/`gallery` в форме проекта ссылаются на уже загруженные пути,
  а не хранят сами файлы.

## Масштабируемость на новые сущности

Новая сущность контента (блог, отзывы, сертификаты) добавляется как:
JSON-файл в `data/` + тип в `types.ts` + редактор в `admin/editors/` +
запись в `admin/registry.ts`. `github.ts` и `lib/data.ts` не меняются — они
уже работают с произвольным путём к файлу.

## UX после сохранения

После успешного PUT — нотификация вида «Сохранено. Деплой займёт ~1–2
минуты» со ссылкой на вкладку Actions репозитория. Pages кэширует
агрессивно: если данные импортируются в бандл на этапе сборки (предпочтительный
вариант из `PLAN.md`), это ожидаемо и не требует доп. cache-busting на
клиенте.
