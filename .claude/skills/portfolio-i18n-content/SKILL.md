# Portfolio i18n & Content Localization

Единая схема мультиязычности для сайта-портфолио. Основной источник истины —
`.ai-factory/DESCRIPTION.md` (раздел «Мультиязычность») и корневой `PLAN.md`.
Этот скилл фиксирует, КАК реализовывать локализацию, чтобы не расходиться
между публичной частью и админкой.

## Два разных вида локализации — не путать

1. **UI-строки** (меню, кнопки, лейблы, тосты) → `react-i18next`.
2. **Контент** (проекты, профиль, скиллы — то, что лежит в `data/*.json`) →
   локализуемые поля прямо внутри JSON, без i18next.

## 1. UI-строки (react-i18next)

- Словари: `src/locales/uk.json`, `src/locales/ru.json`, `src/locales/en.json`.
- Плоская или неглубоко вложенная структура ключей, пример:
  ```json
  { "nav": { "projects": "Проєкти", "about": "Про мене" }, "actions": { "save": "Зберегти" } }
  ```
- Компоненты используют `useTranslation()` и `t('nav.projects')`. Никогда не
  хардкодить UI-текст напрямую в JSX.
- Инициализация i18next читает текущую локаль из hash-роута (см. ниже), а не
  из `navigator.language`.

## 2. Локализуемый контент (JSON-данные)

- Тип-хелпер в `src/types.ts`:
  ```ts
  export type Localized<T = string> = { uk: T; ru?: T; en?: T };
  ```
- Обязательна только `uk`. `ru`/`en` опциональны — при отсутствии значение
  фолбэкается на `uk`.
- Поля схемы, которые обязаны быть локализуемыми (см. `PLAN.md`):
  `title`, `shortDescription`, `description` в `projects.json`; `bio`,
  `title` в `profile.json`.
- Хук доступа:
  ```ts
  // src/lib/useLocalized.ts
  export function useLocalized<T>(field: Localized<T>): T {
    const { locale } = useLocale(); // текущая локаль из роута
    return field[locale] ?? field.uk;
  }
  ```
- Никогда не делать `field['uk']` напрямую в компонентах публичной части —
  всегда через `useLocalized()`, чтобы фолбэк был в одном месте.

## 3. Локаль в роутинге (HashRouter)

- Формат: `#/uk/projects`, `#/ru/projects`, `#/en/projects`.
- Корень `#/` редиректит на сохранённую в `localStorage` локаль, а при её
  отсутствии — на `#/uk/...`.
- Переключатель локали в шапке меняет только сегмент локали в URL, не роут
  целиком, и сохраняет выбор в `localStorage`.
- `<html lang="...">` синхронизируется с текущей локалью роута (эффект на
  верхнем уровне роутера, не в каждой странице).
- Мета-теги / OpenGraph для страницы берутся из `Localized<T>` полей текущей
  локали с тем же фолбэком на `uk`.
- Админка (`/#/admin/...`) НЕ участвует в этой схеме — у неё нет локали в
  URL, только UI-язык через react-i18next (если админка вообще
  переводится — иначе фиксированный язык интерфейса).

## 4. Редакторы админки: табы UK/RU/EN

- Каждое локализуемое поле формы рендерится как `shadcn/ui` `Tabs` с
  вкладками `UK`, `RU`, `EN` — одна форма, значения хранятся в одном объекте
  `Localized<T>` в состоянии формы.
- Вкладка `UK` визуально помечена как обязательная (например, `*` в лейбле
  таба); `RU`/`EN` — необязательные, пустое значение = не сохранять ключ
  вовсе (не сохранять `""`), чтобы фолбэк на `uk` срабатывал на чтении.
- При сохранении объект пишется как есть в JSON через `github.ts` — никакой
  отдельной трансформации для локализации не требуется.

## Чек-лист при добавлении новой текстовой сущности

1. Это UI-строка (кнопка/лейбл/сообщение)? → добавить ключ во все три
   словаря `src/locales/*.json`.
2. Это контентное поле (текст, который редактируется в админке и относится
   к конкретному проекту/профилю)? → тип `Localized<string>` в `types.ts`,
   таб UK/RU/EN в соответствующем редакторе, `useLocalized()` на публичной
   стороне.
3. Не создавать третий вариант локализации (например, отдельный JSON per
   locale) — схема одна на весь проект.
