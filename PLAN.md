# Portfolio Site — план реализации

Спецификация для Claude Code. Проект: личный сайт-портфолио с админкой без бэкенда и без БД. Хостинг — GitHub Pages, данные — JSON в репозитории, сохранение из админки — коммит через GitHub Contents API.

## Цель

Статичный сайт-портфолио, который собирается за выходные, стоит 0 грн/мес и редактируется через собственную админку прямо в браузере.

## Принципы

- Никакого сервера. Всё работает как статика на GitHub Pages.
- Данные — единственный источник правды — лежат в репо (`/data/*.json`, `/public/uploads/`).
- Сохранение в админке = commit + push через GitHub REST API с fine-grained PAT.
- Изменения на проде появляются после пересборки Pages (~1–2 мин) — это ожидаемое поведение.

## Стек

- **React 18 + Vite + TypeScript** (если в процессе решу Vue 3 — архитектура не меняется, только слой компонентов)
- **React Router** в режиме `HashRouter` (избегаем 404-хака на Pages)
- UI: **Tailwind + shadcn/ui** (shadcn ставится через CLI, компоненты копируются в `src/components/ui/` — использовать и в публичной части, и в админке)
- i18n: **react-i18next** (см. раздел «Мультиязычность»)
- Без state-менеджера: контекст + fetch JSON достаточно
- Деплой: GitHub Actions → GitHub Pages

## Схема данных

`projects.json` — массив объектов:

```json
{
  "id": "example-project",
  "title": { "uk": "…", "ru": "…", "en": "…" },
  "slug": "example-project",
  "shortDescription": { "uk": "…", "ru": "…", "en": "…" },
  "description": { "uk": "markdown-текст", "ru": "…", "en": "…" },
  "stack": ["React", "Vite"],
  "role": "Fullstack developer",
  "year": 2026,
  "url": "https://…",
  "cover": "/uploads/example-cover.webp",
  "gallery": ["/uploads/example-1.webp"],
  "featured": true,
  "order": 1,
  "published": true
}
```

`profile.json`: `name`, `title`, `bio` (markdown), `location`, `email`, `socials[]`, `avatar`.
`skills.json`: массив категорий `{ "category": "Frontend", "items": ["…"] }`.

Все типы описать в `src/types.ts` и использовать и на публичной части, и в админке.

## Публичная часть

Страницы:
1. **Home** — hero (из profile.json), featured-проекты, стек, CTA-контакт.
2. **Projects** — грид всех `published: true`, сортировка по `order`.
3. **ProjectDetail** — по slug: галерея, описание (рендер markdown), стек, ссылка.
4. **About** — био + skills.

Требования: адаптив, тёмная/светлая тема по `prefers-color-scheme`, `loading="lazy"` для картинок, мета-теги и OG из profile.json.

## Админка

Роут `/#/admin`, ссылок на него на публичной части нет.

### Авторизация
- Компонент TokenGate: поле для fine-grained PAT (права: только этот репозиторий, `Contents: Read and write`).
- Токен проверяется запросом `GET /repos/{owner}/{repo}` и сохраняется в `localStorage`.
- Кнопка «выйти» = очистить localStorage.
- Токен никогда не попадает в код и в коммиты.

### Сохранение (github.ts)
Алгоритм записи файла:
1. `GET /repos/{owner}/{repo}/contents/{path}` → взять текущий `sha`.
2. `PUT` туда же с `{ message, content: base64(json), sha }`.
3. При 409 (sha устарел) — повторить GET и PUT один раз, потом показать ошибку.

Осмысленные commit messages: `admin: update projects.json (edit "viva-realtyexpert")`.

### Редакторы
- CRUD проектов: список, форма (все поля схемы), toggle `published`, drag-and-drop или поле `order`.
- Редактор profile.json и skills.json.
- Markdown-поля — обычный textarea с превью, без WYSIWYG.

### Картинки
- Загрузка файла → сжатие в браузере через canvas в **webp** (max 1600px по ширине, quality ~0.8) → base64 → PUT в `public/uploads/{slug}-{n}.webp`.
- В форме проекта поле cover и галерея ссылаются на загруженные пути.

### UX после сохранения
После успешного коммита показать нотификацию: «Сохранено. Деплой займёт ~1–2 минуты» со ссылкой на вкладку Actions.

## Масштабируемость

Каждая сущность контента = тройка «JSON-файл в `/data/` + тип в `types.ts` + редактор в `admin/editors/`». Добавление новой сущности (блог, отзывы, сертификаты) не трогает остальной код: генерик-хелперы в `github.ts` и `lib/data.ts` работают с любым файлом по пути. В админке список редакторов собирается из конфига `admin/registry.ts` — новая сущность = одна запись в реестре + компонент формы.

## Мультиязычность (uk / ru / en, основной — uk)

- **UI-строки** (меню, кнопки, подписи): `react-i18next`, словари в `src/locales/{uk,ru,en}.json`.
- **Контент**: локализуемые поля в JSON — объекты вида `"title": { "uk": "…", "ru": "…", "en": "…" }`. Тип-хелпер `Localized<string>` в `types.ts`, хук `useLocalized()` достаёт значение по активной локали с фолбэком на `uk`.
- **Роутинг**: локаль в хеш-маршруте — `#/uk/projects`, `#/en/projects`; редирект `#/` → `#/uk/…` (или сохранённая в localStorage локаль). Переключатель в шапке.
- **Админка**: в редакторах локализуемые поля рендерятся табами UK / RU / EN (shadcn Tabs) — одна форма, три вкладки. Обязательна только uk-версия, остальные при пустоте фолбэкаются.
- Мета-теги и OG — локализованные, `lang` на `<html>` меняется с локалью.

## Контактная форма и лиды → Telegram

Писать лиды в репозиторий нельзя (write-токен в клиентском коде = репо открыт всем). Лиды уходят в Telegram.

**Важно: слать в Bot API напрямую из браузера нельзя** — запрос вида `api.telegram.org/bot<TOKEN>/sendMessage` светит токен бота в клиентском коде, и любой сможет управлять ботом. Токен прячем за бесплатным релеем на Google Apps Script:

1. Создать бота через @BotFather, получить токен. Написать боту `/start`, узнать свой `chat_id` (через `getUpdates`).
2. Apps Script: `doPost(e)` парсит JSON формы, валидирует (honeypot-поле пустое, есть email или message) и делает `UrlFetchApp.fetch` на `sendMessage` с токеном и chat_id, зашитыми в Script Properties. Задеплоить как Web App (access: anyone).
3. Форма на сайте: `fetch(APPS_SCRIPT_URL, { method: "POST", body: JSON.stringify(data) })`. В коде сайта только URL скрипта — токен бота наружу не выходит.

Формат сообщения: имя, email, текст, страница, локаль, дата. Лиды читаются прямо в TG (push из коробки) — отдельная страница «Лиды» в админке не нужна.

Анти-спам: honeypot + минимальная задержка отправки на клиенте, rate-limit по времени в Apps Script (CacheService). Капчу не ставим.

## Деплой

`.github/workflows/deploy.yml`: on push to `main` → `npm ci` → `vite build` → `actions/deploy-pages`. В настройках репо Pages: Source = GitHub Actions. В `vite.config.ts` выставить `base`, если сайт не на кастомном домене.

## Этапы

**Этап 0 — каркас.** Vite + React + TS, роутер, workflow деплоя, пустые JSON с валидной схемой. ✅ Критерий: пустой сайт открывается на Pages.

**Этап 1 — публичная часть + i18n.** Все 4 страницы читают данные из JSON; react-i18next и локаль в роуте с первого дня (ретрофит мультиязычности дороже). ✅ Критерий: контент правится в JSON руками → после пуша меняется на сайте; переключение uk/ru/en работает.

**Этап 2 — админка: данные.** TokenGate, github.ts, CRUD проектов + редакторы profile/skills. ✅ Критерий: правка в админке → коммит в репо → сайт обновился.

**Этап 3 — админка: картинки.** Сжатие и загрузка изображений. ✅ Критерий: загруженная картинка ≤ 300 КБ и отображается в проекте.

**Этап 4 — лиды.** Контактная форма (shadcn Form + zod-валидация) → Apps Script релей → Telegram-бот. ✅ Критерий: отправка формы приходит сообщением в TG; токен бота отсутствует в бандле.

**Этап 5 — полировка.** Темы, мета-теги, lighthouse ≥ 90 по всем категориям, favicon, README.

## Не делаем (осознанно)

- OAuth-логин через GitHub — требует сервера/прокси для client_secret. PAT достаточно для одного пользователя.
- БД, поиск, комментарии, аналитика на бэке — вне скоупа v1.
- Запись лидов в репозиторий/CSV в git — невозможно без утечки write-токена; лиды идут в Telegram через Apps Script релей (см. раздел выше).
- Прямые запросы к Telegram Bot API из браузера — токен бота нельзя светить в клиентском коде.
- WYSIWYG-редактор — markdown + превью.
- Черновики с отдельным стейтом — роль черновика выполняет `published: false`.

## Подводные камни (учесть в коде)

- GitHub Contents API ограничен файлами до ~1 МБ через JSON PUT — сжатие картинок обязательно.
- `sha`-конфликт при параллельных правках — обработать 409.
- Pages кэширует агрессивно — у JSON-запросов на публичной части добавить `?v=` из build-hash или импортировать JSON в бандл на этапе сборки (тогда данные обновляются вместе с деплоем — предпочтительный вариант).
- PAT имеет срок жизни — при 401 показывать TokenGate заново, а не молча падать.
