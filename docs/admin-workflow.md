# Admin workflow

Как редактировать контент сайта (проекты, профиль, скиллы, картинки) через встроенную браузерную админку — без бэкенда и без базы данных.

## Доступ

- Скрытый роут: `/#/admin`.
- Точка входа — `TokenGate` (`app/src/admin/components/TokenGate/`): вводишь fine-grained Personal Access Token с правами только на этот репозиторий (`Contents: Read/Write`).
- Токен проверяется запросом к `GET https://api.github.com/repos/{owner}/{repo}`, а не просто сохраняется вслепую.
- Токен хранится только в `localStorage` — никогда не попадает в код, бандл или коммиты. Кнопка «выйти» очищает `localStorage` и возвращает на `TokenGate`.
- Если API отвечает `401` (истёкший/невалидный токен) — админка сбрасывает на `TokenGate` заново, а не падает молча и не зацикливается.

## Редактирование сущностей

Каждая сущность контента — это тройка «JSON-файл в `app/data/` + тип в `types.ts` + редактор в `app/src/admin/editors/`», зарегистрированная в `app/src/admin/lib/registry.ts` (редакторы-одиночки: Profile, Skills) или в собственных роутах (Projects — список/CRUD, Taxonomies):

- **Проекты** — CRUD (создание, редактирование, удаление, сортировка по `order`), markdown-поле описания с превью.
- **Profile** (`data/profile.json`) — имя, титул, био (markdown), контакты, соцсети.
- **Skills** (`data/skills.json`) — стек и категории.
- **Taxonomies** (`data/taxonomies.json`) — управляемые словари stack/category/role.

Новая сущность (блог, отзывы, сертификаты) добавляется без изменения общего кода админки — просто новая запись в `registry.ts` + свой редактор.

## Сохранение — единая точка, батчами

С этапа «Батчинг сохранений» правки **не коммитятся по мере ввода**. Вместо этого:

- Каждый редактор, включая Taxonomies и удаление проекта в ProjectsList, держит свои несохранённые изменения в общем черновике сессии — `AdminDraftContext` (`app/src/admin/components/AdminDraftContext/`), зеркалируемом в `localStorage` (ключ `admin-draft-v1`). Можно свободно переключаться между разделами админки (отредактировать один проект, перейти к другому, поправить профиль) — черновики каждой сущности копятся независимо, а повторная загрузка одного и того же файла (например, `taxonomies.json`, который читает и сам TaxonomyEditor, и выпадающие списки ProjectForm) не затирает уже начатую правку.
- Единственная точка сохранения — плавающая кнопка **«Сохранить всё (N)»** внизу справа (`app/src/admin/components/SaveAllButton/`), появляется, только когда есть несохранённые правки. По клику черновики всех изменённых сущностей уходят в GitHub по очереди, каждый — своим коммитом; после успешного сохранения соответствующая запись пропадает и из `localStorage`.
- Черновик **переживает перезагрузку и закрытие вкладки** (восстанавливается из `localStorage` при следующем открытии `/#/admin`) — очищается только по факту сохранения (полностью или по мере флаша каждой сущности), не по времени или по закрытию вкладки. Ещё не загруженные картинки (`PendingImage`) при этом кодируются в base64 — при большом объёме несохранённых изображений возможно упереться в квоту `localStorage`, тогда правки остаются видны только пока открыта вкладка (с предупреждением тостом).

## Загрузка изображений

- Файл сжимается прямо в браузере через `<canvas>` в **webp** (до ≤300 КБ) сразу при выборе — без сети.
- Сама загрузка в GitHub **отложена**: до нажатия «Сохранить всё» картинка хранится только в памяти (`{blob, previewUrl}`), превью рисуется через локальный `URL.createObjectURL`. Реальный `PUT` в `app/public/uploads/` происходит вместе с сохранением сущности, которой принадлежит картинка (`app/src/admin/lib/resolvePendingImages.ts`).
- Это же убирает старую проблему «осиротевших» файлов: если бросить форму с выбранной, но не сохранённой картинкой, в репозитории ничего не остаётся — до `resolvePendingImages` дело просто не доходит.
- GitHub Contents API ограничивает PUT примерно 1 МБ на файл — сжатие обязательно, а не опционально.

## Как устроено сохранение (GitHub Contents API)

Подробности — `.claude/skills/portfolio-admin-github-write`. Единственная точка записи — `app/src/admin/lib/github.ts`.

Обязательный порядок для **каждого** коммита в пачке, отправляемой по клику «Сохранить всё»:

1. `GET /repos/{owner}/{repo}/contents/{path}` → взять текущий `sha`.
2. `PUT /repos/{owner}/{repo}/contents/{path}` с телом `{ message, content: base64(...), sha }`.
3. При ответе **409** (sha устарел, файл изменили параллельно) — повторить шаги 1–2 **один раз**. Если и повторная попытка даёт 409 — показывается явная ошибка («файл изменён параллельно, обновите страницу»), без тихого отката и без зацикливания на ретраях; эта конкретная сущность остаётся несохранённой, остальные из пачки продолжают сохраняться.
4. После успешного сохранения — тост «Сохранено (N). Деплой займёт ~1–2 минуты».

## ⚠️ Та же оговорка про `main`

Каждое сохранение из админки — это **коммит напрямую в `main`**, ту же ветку, в которую пушится и локальная разработка (клик по «Сохранить всё» на несколько правок — это несколько последовательных коммитов, не один). Это значит, что параллельная локальная сессия разработки может закоммитить/запушить что-то, не зная о правках, только что сделанных через админку (и наоборот).

Правило и объяснение — в [dev-workflow.md](./dev-workflow.md) (раздел «Главная оговорка про `main`»): перед началом любой локальной сессии разработки всегда делать `git pull origin main`.
