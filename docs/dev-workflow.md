# Dev workflow

Как разрабатывать этот проект локально: структура, команды, деплой и главная оговорка про общую ветку `main`.

## Структура репозитория

Всё приложение — код и build-конфигурация — лежит в `app/`. Корень репозитория содержит только dev/AI-tooling (`.ai-factory/`, `.claude/`, `.github/`, `AGENTS.md`, `PLAN.md`) — эти файлы там нужны, потому что сами инструменты (git, GitHub Actions, Claude Code) ищут их только в истинном корне. Подробнее — `AGENTS.md`.

## Установка и локальный запуск

```bash
git clone https://github.com/Sunder23/portfolio.git
cd portfolio/app
npm install
npm run dev
```

Dev-сервер (Vite) поднимется с хот-релоадом.

## Проверка сборки перед пушем

Перед тем как пушить в `main`, стоит убедиться, что прод-сборка проходит без ошибок:

```bash
npm run build
```

Это тот же шаг, который выполняет `.github/workflows/deploy.yml` в CI (`tsc -b && vite build`, working directory — `app/`). Если он падает локально — упадёт и в CI.

## Деплой

Деплой полностью автоматический:

```
git push origin main
  → GitHub Actions (.github/workflows/deploy.yml)
    → npm ci && npm run build (working-directory: app)
    → upload-pages-artifact (app/dist)
    → deploy-pages
  → GitHub Pages обновится через ~1-2 минуты
```

Ручных шагов после пуша нет — ничего дополнительно нажимать не нужно, просто подождать.

## Lighthouse-аудит

Прогонять Lighthouse (`npm run build && npm run preview` в `app/`, затем аудит открытой страницы) нужно **вручную через Chrome DevTools**, а не через `npx lighthouse` из headless-скрипта: в песочнице AI-агента headless Chrome не может отрисовать страницу (`NO_FCP`) даже с флагами software-рендеринга — это ограничение окружения, не баг сайта. См. также правило про Playwright в `.ai-factory/RULES.md`.

## ⚠️ Главная оговорка: `main` — общая ветка с админкой

Локальная разработка и встроенная админка (`/#/admin`) коммитят в одну и ту же ветку `main`:

- Ты пушишь изменения из терминала.
- Кто-то (в т.ч. ты сам) правит контент через админку — она пишет коммиты напрямую в `main` через GitHub Contents API (см. [admin-workflow.md](./admin-workflow.md)).

**Правило: делай `git pull origin main` перед началом любой локальной сессии разработки — даже если ты только что сам туда запушил.**

Почему это важно именно "даже сразу после своего пуша": между твоим пушем и следующей локальной сессией админка могла закоммитить правки контента (например, новый проект или картинку). Если начать работать со старым локальным `main` и запушить без предварительного `pull`, следующий пуш может:

- конфликтовать с изменениями из админки, или
- тихо затереть их (если merge пройдёт "чисто", но твоя локальная копия данных была устаревшей).

```bash
git checkout main
git pull origin main
# дальше — обычная работа: ветка/правки/commit/push
```
